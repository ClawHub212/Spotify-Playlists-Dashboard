# Spotify Dashboard

Local web dashboard + native macOS wrapper that shows which of your playlists contain the currently playing Spotify track, with one-click add/remove.

## Stack & entry points

- **Backend**: Flask (`app.py`), port **8888**, Spotify via `spotipy`. Run: `.venv/bin/python app.py` (system `python3` lacks the deps).
- **Frontend**: vanilla JS — `static/script.js` + `playlists.html` / `tracker.html` / `queue.html` + `styles.css`. No build step; served with no-cache headers.
- **Desktop app**: `desktop/SpotifyDashboard/` (Swift, no Xcode project). Build: `desktop/SpotifyDashboard/build.sh` → installs to `/Applications/Spotify Dashboard.app`; add `--relaunch` to restart the app on the checkout you built from, in the background. Launch: `desktop/run.sh`.

## Architecture

- `config.json` (gitignored; see `config.example.json`) defines the pages and their playlists; the playlist editor UI writes back to it live.
- Backend caches every playlist's track URIs in background threads at startup (2s/playlist — warm-up takes a couple of minutes; endpoints report it via the `X-Loading-State` header). The cache **persists across restarts** in `playlist_cache.json` (gitignored, symlinked from main like the other runtime files, saved per playlist during warm-up and on every toggle) so a fresh launch answers `/api/check-playlists` correctly immediately. Cache-dict membership means "real data": never pre-seed an empty set for a playlist (that silently disables the live-check fallback and made launch report the current track as saved nowhere, 08-28-26). `/api/check-playlists` sends `X-Cache-State: warming|ready`; the frontend re-checks every 10s while warming.
- The native loading screen lifts only when `window.__trackReady === true` **and** `window.__gridReady !== false` (real tiles rendered, not the skeleton; `!== false` so an older frontend that never defines the flag doesn't stall the loader), with a 30s cap — a new "page is ready" condition must flip one of these flags, not add a new poll. Every launch appends which dismissal path fired to `<served checkout>/loader-debug.log` (gitignored) — read that file before guessing at loading-screen bugs.
- The frontend instant-renders from `localStorage` on every page load: `lastKnownTrack` (header), `cachedPlaylists.<pageId>` (the grid — so the skeleton only appears on a true first run), and `lastActiveIds` (which tiles are lit). The live fetches then correct the render. An empty/interim fetch result must never clobber an already-rendered cached grid.
- The native app finds `app.py` via `SPOTIFY_DASHBOARD_PATH` env, then the `SpotifyDashboardProjectRoot` stamped into `Info.plist` (always the MAIN checkout), then a saved bookmark, then scanning (rename-proof).
- **To run a worktree's code without merging:** `scripts/dashboard-open.sh` picks the most recently touched checkout (or takes `main` / a branch / a path), symlinks the gitignored runtime files (`.env`, `config.json`, `.cache`, `.venv`) from main into it, and relaunches the app with `SPOTIFY_DASHBOARD_PATH` set — only when the app isn't already serving that checkout, since a switch costs a Flask restart + cache warm-up. Add `--background` to relaunch without stealing focus (`SPOTIFY_DASHBOARD_BACKGROUND_LAUNCH=1` makes the launch-time window order back). All three Keyboard Maestro launchers run it, then send their own `show page` and notify which branch went live — they are one surface and change together, so a launch-behavior change goes into all three in the same pass — **Playlist** `03C502E9-2CB8-4AE9-B401-94AACA5BEC3F`, **Tracker** `60457DEF-F65C-4526-9EFC-D2BADE3AA12B`, **Queue** `5317C887-D906-49AD-BEAA-BE8AFDAFD450`. It also restarts a running app that predates the installed binary, so a rebuild goes live on the next trigger. Swift changes still need `build.sh` — the launcher warns when the branch's Swift is newer than the installed binary, and `build.sh --relaunch` just delegates back to this script (`<checkout> --background`), so there is exactly one relaunch implementation to keep correct.
- The last menu-bar menu (`VersionMenuController.swift`) names the checkout being served — `⎇ <human name> · <relative time>` — with branch, path, when the code last changed, a stale-binary warning, and **Open in Claude Code**. A menu-bar item renders its **submenu's** title, not the item's, so both must be set.
- **Worktree names** come from, in order: `~/.claude/worktree-labels.json` (set with `scripts/name-worktree.sh "Human Name"`, keyed by path, outside the repo so it never touches git status) → the Claude Code chat's own title → the branch cleaned up (`claude/playlist-emoji-display-name-977537` → "Playlist Emoji Display Name"). So the menu normally mirrors the chat name in Claude Code's sidebar with no setup.
- **Open in Claude Code** reads the desktop app's session store (`~/Library/Application Support/Claude/claude-code-sessions/<org>/<user>/local_*.json` — cwd, title, `sessionId`, `cliSessionId`, `isArchived`) and opens **`claude://claude.ai/epitaxy/local_<id>`**, which navigates the app to that exact chat. The host must be `claude.ai` (`epitaxy` is the Code surface's internal route); `claude://epitaxy/…`, `claude://local_sessions/…` and `claude://code/…` are not dispatched. `claude://resume?session=<cli id>` is the fallback only — it *imports* a transcript, so on a chat the app already holds it spawns a second untitled copy ("General coding session"). Verified 08-15-26 by watching `lastFocusedAt` in the store.
- `build.sh` installs to `/Applications` and deletes its staging copy, so exactly one `Spotify Dashboard.app` exists on disk — two bundles with the same identifier let LaunchServices/AppleScript launch a stale build.
- `/api/open-in-spotify` POSTs run `open spotify:playlist:<id>` locally to open the Spotify desktop app.
- The header repeat icon is also a Keyboard Maestro hook: `/api/toggle-repeat` fires the **Repeat Toggle** macro (`91EEA4DF-857F-415B-93D8-4584BCD4E92B`, group "Spotify Dashboard - External") through the `keyboardmaestro` CLI with `-p On|Off`; the macro branches on `%TriggerValue%` to mirror the state into `xbarrepeat__status` / `nRepeatStatus`. Trigger it with a parameter or it always reads as Off.

## Gotchas

- Secrets/config at repo root: `.env`, `.cache` (Spotify token), `config.json` — all gitignored; never commit or `git add -A`.
- Spotify refresh tokens expire ~6 months (2026-07-20 policy); 401s redirect the UI to `/login`, and `is_authenticated()` clears dead tokens.
- Frontend edits only need a browser/page reload (no-cache headers); `app.py` edits need a backend restart — `scripts/dashboard-open.sh <checkout> --background --restart` (the launcher otherwise skips an already-live checkout, so a plain run leaves the old Python serving).
- The NAGA NEXT SHOW tiles get a special holographic treatment (`isSpecialPlaylist` in `script.js`) — keep it in any restyle.
- Grid keyboard shortcuts (N/E/C/S/F defaults, plus THEME on ⌘⇧L) are stored in `localStorage` (`gridShortcuts.v1`); the model (defaults, labels, matching) is `static/grid-shortcuts.js`, shared by every page and the Settings page — edit it there only. The native layer swallows only the sidebar shortcut (default ⌘S) and the Settings combos. CANCEL (C, and always Esc) leaves whichever mode is armed. The Playlists filter box takes F (rebindable) plus `/` and ⌘F always.
- The native app builds its whole menu bar by hand (`AppDelegate.buildMenu`) — text-editing behavior inside the web view (⌘X/⌘C/⌘V/⌘A, ⌃⌘Space emoji palette) exists only because the Edit menu supplies those key equivalents. Don't drop it.
- **Settings is ONE surface**: `static/settings.html` + `settings.js` (served at `/settings`, no auth) hosted by the native Settings window (`SettingsWindowController.swift` — resizable, frame persisted under `SettingsWindow`, ⌘, opens, ⌘` toggles, ⌃G/⌃A/⌃S jump to General/Appearance/Shortcuts and are rebindable). Native-owned preferences (global hotkeys, app mode, float on top, sidebar + section shortcuts) round-trip through the `settings` script-message bridge; grid shortcuts and the theme are shared with the dashboard through same-origin `localStorage`. The dashboard reports theme changes over the `dashboard` bridge so the menu-bar **Themes** menu (Phosphor ☾ / Daybreak ☀, ✓ on the active one) stays right. There is no in-page shortcuts modal anymore — add a preference by extending the model in `settings.js`, never a second surface. The old manual-frame AppKit window (and its clipping gotcha) is gone.
- Dual theme: dark default + "Daybreak" light (`localStorage` `dashTheme`, `body.theme-light`). All colors flow from the token sheet at the top of `styles.css` — never hardcode a surface color outside it; light overrides live in the `body.theme-light` blocks.
- The Playlists grid must never crop: `.playlist-grid` is a flex item (`flex: 1; min-height: 0`) filling the section **below** the NEW/EDIT/SPOTIFY actions row — never give it `height: 100%` (that sized it past the section and clipped the bottom rows at every window height, 08-28-26). The inactive group defaults to 3 columns but `renderPlaylists()` adds columns when the window is too short for readable rows (min row ≈ one text line + padding; column count capped by width/260px), re-computed on resize/section-box changes via `scheduleGridRerender()`.
- Every page has the sidebar aside (`#artist-sidebar`), but it shows different content: the artist's latest release on Playlists + Tracker, and the **current album's tracklist** on Queue (`showArtistSidebar` dispatches to `showAlbumSidebar`; `/api/album-tracks` is cached per album, the playing row gets the orange equalizer, hover ▶ / double-click plays that track in album context via `/api/play-album-track`). Whether it exposes *itself* — on an add, and on Queue once on load — is the `#sidebar-auto-toggle` header button next to the theme toggle (`localStorage` `sidebarAutoReveal`, default on) — opening it by hand (edge handle, ⌘S) always works regardless, and an already-open sidebar still refreshes on add. Any new auto-open path must go through the same `sidebarAutoReveal || sidebarState.isOpen` guard.
- Tracker/Queue divider entries accept an optional `"label"` in `config.json` — labeled dividers render their section as a vertical rail; unlabeled ones stay plain separator lines.
- `build.sh` ends with a `--relaunch` block whose last statement is `exec` — it never returns. Anything appended after it is dead code that runs on no build, silently. New tail logic goes **above** that block; the debug-worktree-menu guard (`~/.claude/skills/mac-worktree-menu/check.sh`, standard on every Mac app) sits there for exactly this reason.
